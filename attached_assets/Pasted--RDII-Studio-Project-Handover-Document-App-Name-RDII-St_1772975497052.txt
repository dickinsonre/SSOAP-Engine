## 1. Project Overview

RDII Studio is a web-based tool for **Rainfall-Derived Infiltration and Inflow (RDII)** analysis of sanitary sewer systems. It guides engineers through a complete workflow:

1. **Import** flow and rainfall time series data (SWMM5, ICM SWMM, ICM InfoWorks, CSV)
2. **QA/QC** the data for quality issues
3. **Separate** Dry Weather Flow (DWF) and Groundwater Infiltration (GWI)
4. **Generate** an observed RDII series
5. **Detect & classify** storm events
6. **Calibrate** RTK parameters using multi-objective optimization (NSGA-II)
7. **Compare** calibration scenarios
8. **Analyze** time series decomposition
9. **Export** results to InfoWorks ICM format
10. **Documentation** with interactive tutorials

The app persists calibration results to a cloud database and supports user authentication.

## 2. Domain Background

### What is RDII?
RDII is stormwater that enters sanitary sewer systems during rainfall via:
- **Inflow** (direct connections like roof drains)
- **Infiltration** (groundwater seeping through pipe joints/cracks)

### The RTK Method
The RTK method models RDII using **three triangular unit hydrographs**, each with 3 parameters (9 total):

| Component | R (Response Ratio) | T (Time to Peak, hrs) | K (Recession Constant) |
|-----------|-------------------|----------------------|----------------------|
| **Fast (1)** | R1 (0–1) | T1 | K1 |
| **Medium (2)** | R2 (0–1) | T2 > T1 | K2 > K1 |
| **Slow (3)** | R3 (0–1) | T3 > T2 | K3 > K2 |

**Constraints:** R1 + R2 + R3 ≤ 1, T1 < T2 < T3, K1 < K2 < K3

### Calibration Objectives (minimized simultaneously)
1. RMSE (Root Mean Square Error)
2. Volume Bias (%)
3. Peak Flow Error (%)
4. Peak Timing Error

## 12. File Format Parsers

**Location:** `src/lib/fileFormatParsers.ts`

### Supported Formats

| Format | Detection Method | Parser Function |
|--------|-----------------|----------------|
| **SWMM5** | `[TIMESERIES]` section, EPA header | `parseSWMM5TimeSeriesFile()` |
| **ICM SWMM** | Innovyze/Autodesk + ICM SWMM headers | `parseICMSWMMExport()` |
| **InfoWorks ICM** | InfoWorks ICM/CS headers, `.prn` extension | `parseInfoWorksExport()` |
| **CSV** | `.csv`/`.tsv` extension fallback | `parseCSVGeneric()` |

### Main Entry Point
```typescript
parseFile(file: File): Promise<{ format: FileFormat; data: ParsedTimeSeriesData[] }>
```
- Detects format via `detectFileFormat()`
- Routes to appropriate parser
- Returns array of `ParsedTimeSeriesData` (one per series in file)

### CSV Parser Requirements
- Must have a column with "date", "time", or "timestamp" in the header (case-insensitive)
- All other numeric columns are parsed as separate series
- Timestamps parsed via `new Date()`

### RLS Policies

RLS is enabled on `calibration_history`. All four policies use `RESTRICTIVE` mode (Permissive: No):

| Policy | Command | Using | With Check |
|--------|---------|-------|------------|
| Users can read their own calibration history | `SELECT` | `auth.uid() = user_id` | — |
| Users can insert their own calibration history | `INSERT` | — | `auth.uid() = user_id` |
| Users can update their own calibration history | `UPDATE` | `auth.uid() = user_id` | `auth.uid() = user_id` |
| Users can delete their own calibration history | `DELETE` | `auth.uid() = user_id` | — |

> **Note:** Because these are RESTRICTIVE (not permissive), authenticated users can ONLY access rows where `user_id` matches their `auth.uid()`. There are no public/anonymous access policies.

```sql
-- Create the calibration_history table
CREATE TABLE public.calibration_history (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID,
  basin_name TEXT NOT NULL,
  basin_type TEXT,
  drainage_area DOUBLE PRECISION,
  imperviousness DOUBLE PRECISION,
  r1 DOUBLE PRECISION NOT NULL,
  t1 DOUBLE PRECISION NOT NULL,
  k1 DOUBLE PRECISION NOT NULL,
  r2 DOUBLE PRECISION NOT NULL,
  t2 DOUBLE PRECISION NOT NULL,
  k2 DOUBLE PRECISION NOT NULL,
  r3 DOUBLE PRECISION NOT NULL,
  t3 DOUBLE PRECISION NOT NULL,
  k3 DOUBLE PRECISION NOT NULL,
  rmse DOUBLE PRECISION NOT NULL,
  volume_error DOUBLE PRECISION NOT NULL,
  peak_error DOUBLE PRECISION NOT NULL,
  nse DOUBLE PRECISION,
  r2_score DOUBLE PRECISION,
  num_storms INTEGER,
  calibration_notes TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Auto-update trigger
CREATE OR REPLACE FUNCTION public.update_updated_at_column()
RETURNS trigger
LANGUAGE plpgsql
SET search_path TO 'public'
AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$;

CREATE TRIGGER update_calibration_history_updated_at
  BEFORE UPDATE ON public.calibration_history
  FOR EACH ROW
  EXECUTE FUNCTION public.update_updated_at_column();

-- Enable RLS
ALTER TABLE public.calibration_history ENABLE ROW LEVEL SECURITY;

-- RLS Policies (RESTRICTIVE)
CREATE POLICY "Users can read their own calibration history"
  ON public.calibration_history FOR SELECT
  USING (auth.uid() = user_id);

CREATE POLICY "Users can insert their own calibration history"
  ON public.calibration_history FOR INSERT
  WITH CHECK (auth.uid() = user_id);

CREATE POLICY "Users can update their own calibration history"
  ON public.calibration_history FOR UPDATE
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

CREATE POLICY "Users can delete their own calibration history"
  ON public.calibration_history FOR DELETE
  USING (auth.uid() = user_id);
```

- **Path:** `supabase/functions/optimize-rtk/index.ts`

- **Purpose:** Runs NSGA-II-style RTK calibration via Lovable AI
- **Input:** `{ rainfallData, flowData, events, bounds, algorithmParams }`
- **AI Model:** `google/gemini-2.5-flash` via `https://ai.gateway.lovable.dev/v1/chat/completions`
- **Output:** `{ solutions: [{ parameters, rmse, volumeError, peakError, nse }] }`
- **Error handling:** 429 (rate limit), 402 (payment required), 500 (general)

### `suggest-parameters`
- **Path:** `supabase/functions/suggest-parameters/index.ts`
- **Auth:** JWT verification disabled
- **Purpose:** AI-powered parameter suggestions based on historical calibrations
- **Input:** `{ basinType, drainageArea?, imperviousness? }` (Zod validated)
- **Process:**
  1. Queries `calibration_history` for similar basins (top 50 by RMSE)
  2. Sends historical data + basin characteristics to AI
  3. Returns suggested RTK parameters with confidence level
- **Output:** `{ suggestion: string, historicalDataCount: number }`

### Shared Configuration
Both functions use:
- `LOVABLE_API_KEY` secret for AI gateway auth
- CORS headers allowing all origins
- `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` for DB access (suggest-parameters only)

## 21. Reproducing the Project

### Prerequisites
- Node.js 18+ or Bun
- Lovable account (for cloud features) OR standalone Supabase project

### Steps to Recreate

1. **Clone/export the repository**

2. **Install dependencies:**
   ```bash
   npm install
   # or
   bun install
   ```

3. **Set up Supabase:**
   - Create a Supabase project
   - Run the migration to create `calibration_history` table (see schema above)
   - Create the `update_updated_at_column()` function
   - Enable RLS and add appropriate policies
   - Deploy edge functions (`optimize-rtk`, `suggest-parameters`)

4. **Configure environment:**
   ```env
   VITE_SUPABASE_URL=your_supabase_url
   VITE_SUPABASE_PUBLISHABLE_KEY=your_anon_key
   ```

5. **Set edge function secrets:**
   ```bash
   supabase secrets set LOVABLE_API_KEY=your_ai_key
   ```

6. **Run locally:**
   ```bash
   npm run dev
   # or
   bun dev
   ```

7. **Deploy:**
   - Lovable: Click "Publish"
   - Self-hosted: `npm run build` → deploy `dist/` to any static host
   - Edge functions: `supabase functions deploy`
